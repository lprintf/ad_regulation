# Facebook Ads 洞察数据同步逻辑

## 概述

本文档详细说明 Facebook Ads Insights 数据的同步机制，包括自动调度、手动触发、数据存储和查询逻辑。

## 核心组件

### 1. 数据模型

#### InsightsDailyDocument (MongoDB Collection: `insights_daily`)
存储每日广告洞察数据的主表。

**字段说明**：
```python
account_id: str          # 广告账号 ID（不带 act_ 前缀）
campaign_id: str         # 广告系列 ID
adset_id: str            # 广告组 ID
ad_id: str               # 广告 ID
date_start: datetime     # 数据日期

# 核心指标
spend: float             # 花费
impressions: int         # 展示次数
reach: int               # 触达人数
clicks: int              # 点击次数
inline_link_clicks: int  # 内联链接点击
outbound_clicks: int     # 出站点击

# 转化事件
landing_page_view: int           # 落地页浏览
onsite_web_checkout: int         # 站内结账
onsite_web_add_to_cart: int      # 加购
onsite_web_purchase: int         # 购买
onsite_web_checkout_value: float # 结账价值
onsite_web_add_to_cart_value: float # 加购价值
onsite_web_purchase_value: float    # 购买价值

# 元数据
fetched_range_start: datetime    # 本次拉取的起始日期
fetched_range_end: datetime      # 本次拉取的结束日期
ingested_at: datetime            # 首次写入时间
updated_at: datetime             # 最后更新时间
```

**索引**：
- `(ad_id, date_start)` - 唯一索引
- `(account_id, date_start)` - 账号查询索引
- `(campaign_id, date_start)` - 广告系列查询索引
- `(adset_id, date_start)` - 广告组查询索引

#### InsightsSyncStateDocument (MongoDB Collection: `insights_sync_state`)
记录每个广告账号的同步状态。

**字段说明**:
```python
account_id: str                  # 广告账号 ID（唯一）
last_synced_at: datetime         # 最后同步时间
last_synced_date: datetime       # 最后同步的数据日期
initial_requested_since: datetime # 首次请求的起始日期
obs_since: datetime              # 观测窗口起始日期
obs_until: datetime              # 观测窗口结束日期
last_status: str                 # 最后状态 (idle, running, success, failed)
last_error: str                  # 最后错误信息
metadata: dict                   # 元数据（包含 range、mode、trigger 等信息）
updated_at: datetime             # 更新时间
```

### 2. 配置参数

#### 关键常量 (`api/services/insights_sync_service.py`)

```python
INSIGHTS_ASYNC_THRESHOLD_DAYS = 7    # 同步/异步模式阈值（天）
REALTIME_LOOKBACK_DAYS = 3           # 实时数据回溯天数
HISTORICAL_MONTH_LOOKBACK = 37       # 历史数据回溯月数
ASYNC_POLL_INTERVAL = 30             # 异步任务轮询间隔（秒）
ASYNC_MAX_ATTEMPTS = 200             # 异步任务最大轮询次数
```

**说明**：
- **日期跨度 ≤ 7 天**：使用同步模式（`sync`），直接调用 Facebook API 获取数据
- **日期跨度 > 7 天**：使用异步模式（`async`），创建 Facebook 异步任务，轮询等待完成
- **最近 3 天数据**：始终从 Facebook API 实时获取（可能有延迟或更新）
- **3 天前数据**：从数据库查询（已入库的历史数据）

## 同步触发方式

### 1. 自动调度（Scheduled Sync）

**调度器**：`insights_sync_scheduler.py`
**任务 ID**：`insights::daily_backfill`
**默认时间**：每天 11:00 UTC
**执行函数**：`InsightsSyncService.run_daily_schedule()`

#### 自动调度逻辑流程

```
1. 获取所有广告账号
   ↓
2. 查询每个账号的同步状态（InsightsSyncStateDocument）
   ↓
3. 计算需要同步的日期范围：
   - 起始日期：max(上次同步日期 + 1, 今天 - 37个月)
   - 结束日期：今天 - 3天（避免实时数据不稳定）
   ↓
4. 如果所有账号都是最新的，跳过同步
   ↓
5. 调用 sync_range() 执行同步
```

**配置管理**：
- Cron 表达式可通过 API 修改
- 状态持久化到 MongoDB `scheduler_state` 集合（`scheduler_state_store`）
- 支持暂停/恢复调度任务

### 2. 手动触发（Manual Trigger）

**API 端点**：`POST /insights/sync/runs`

**请求示例**：
```bash
curl -X POST "http://localhost:8000/insights/sync/runs" \
  -H "Content-Type: application/json" \
  -H "X-User-Id: user123" \
  -d '{
    "account_ids": ["1244295750378353", "act_1279567647104057"],
    "since": "2025-07-01",
    "until": "2025-10-31"
  }'
```

**参数说明**：
- `account_ids`：要同步的账号 ID 列表（可选，为空则同步所有账号）
- `since`：起始日期（YYYY-MM-DD）
- `until`：结束日期（YYYY-MM-DD）

**返回结果**：
```json
{
  "success": true,
  "data": {
    "total_accounts": 2,
    "processed_accounts": {
      "1244295750378353": {
        "mode": "async",
        "since": "2025-07-01",
        "until": "2025-10-31",
        "records": 3520,
        "trigger": "manual",
        "triggered_by": "user123"
      }
    },
    "failed_accounts": {}
  }
}
```

## 同步执行流程

### 核心方法：`sync_range()`

```
输入参数：
- since: 起始日期
- until: 结束日期
- mode: "auto" (自动调度) 或 "manual" (手动触发)
- triggered_by: 触发者 ID

执行步骤：
1. 验证日期范围（since ≤ until）
   ↓
2. 获取所有广告账号和同步状态
   ↓
3. 遍历每个账号，计算实际同步范围：
   ├─ account_start = max(since, 今天 - 37个月, 上次同步日期 + 1)
   ├─ 如果 account_start > until，跳过该账号
   └─ 计算日期跨度 days = (until - account_start).days + 1
   ↓
4. 根据日期跨度选择同步模式：
   ├─ days ≤ 7：添加到 sync_ranges（同步模式）
   └─ days > 7：添加到 async_ranges（异步模式）
   ↓
5. 更新同步状态（InsightsSyncStateDocument）：
   ├─ last_status = "running"
   ├─ initial_requested_since = 本次起始日期
   ├─ obs_since / obs_until = 观测窗口
   └─ metadata.range = {since, until, mode, trigger, triggered_by}
   ↓
6. 如果总天数 > 365，临时删除索引（加速写入）
   ↓
7. 并行处理账号：
   ├─ _process_sync_accounts(sync_ranges)
   │   └─ 调用 _fetch_insights_sync()
   │       └─ 调用 Facebook API get_daily_insight()
   │       └─ 批量写入数据库 _bulk_upsert_insights()
   └─ _process_async_accounts(async_ranges)
       └─ 调用 _fetch_insights_async()
           └─ 创建 Facebook 异步任务
           └─ 轮询任务状态（每 30 秒）
           └─ 任务完成后获取结果
           └─ 批量写入数据库 _bulk_upsert_insights()
   ↓
8. 恢复索引（如果之前删除过）
   ↓
9. 更新同步状态：
   ├─ last_status = "success" 或 "failed"
   ├─ last_synced_date = until
   ├─ last_synced_at = 当前时间
   └─ last_error = 错误信息（如果失败）
   ↓
10. 返回同步结果
```

### 数据写入：`_bulk_upsert_insights()`

使用 MongoDB 批量 upsert 操作，避免重复数据：

```python
operations = [
    UpdateOne(
        {"ad_id": ad_id, "date_start": date_start},  # 查询条件
        {
            "$set": {
                "account_id": ...,
                "campaign_id": ...,
                "adset_id": ...,
                # ... 所有指标
                "fetched_range_start": ...,
                "fetched_range_end": ...,
                "updated_at": now
            },
            "$setOnInsert": {"ingested_at": now}  # 仅在新建时设置
        },
        upsert=True
    )
]
collection.bulk_write(operations, ordered=False)
```

**特点**：
- **幂等性**：重复执行不会产生重复数据
- **可重试**：失败后可以安全重新同步
- **性能优化**：批量操作，大数据量时禁用索引

## 数据查询接口

### 1. 数据库查询（推荐用于查看历史数据）

**端点**：`GET /insights`
**数据源**：**仅 MongoDB 数据库**（不调用 Facebook API）

**使用场景**：
- 查看已同步的历史数据
- 快速查询，无需等待 API 响应
- 前端"洞察数据浏览"页面使用此接口

**请求示例**：
```bash
# Ad 级别查询（默认）
curl -X GET "http://localhost:8000/insights?ad_account_id=1244295750378353&since=2025-07-22&until=2025-08-31&time_increment=1" \
  -H "X-User-Id: user123"

# AdSet 级别查询（按广告组聚合）
curl -X GET "http://localhost:8000/insights?ad_account_id=1244295750378353&since=2025-07-22&until=2025-08-31&level=adset&time_increment=1" \
  -H "X-User-Id: user123"

# Campaign 级别查询（按广告系列聚合）
curl -X GET "http://localhost:8000/insights?ad_account_id=1244295750378353&since=2025-07-22&until=2025-08-31&level=campaign&time_increment=1" \
  -H "X-User-Id: user123"
```

**参数说明**：
- `ad_account_id`：广告账号 ID（支持带或不带 `act_` 前缀）
- `since`：起始日期（YYYY-MM-DD）
- `until`：结束日期（YYYY-MM-DD）
- `level`：聚合级别，支持 `"ad"`、`"adset"`、`"campaign"`
  - `"ad"`：广告级别（无聚合）
  - `"adset"`：广告组级别（按 adset_id 和 date 聚合）
  - `"campaign"`：广告系列级别（按 campaign_id 和 date 聚合）
- `time_increment`：时间粒度，目前仅支持 `1`（按日）
- `breakdowns`：暂不支持

**响应数据结构**：

响应中的 `InsightRecord` 包含以下字段：
```typescript
{
  ad_id: string,        // 实体 ID（向后兼容字段）
  adset_id?: string,    // 广告组 ID（仅当 level="adset" 时填充）
  campaign_id?: string, // 广告系列 ID（仅当 level="campaign" 时填充）
  date: string,         // 日期（YYYY-MM-DD）
  metrics: {...}        // 指标数据
}
```

**不同聚合级别的响应示例**：

1. **Ad 级别** (`level="ad"`)：
```json
{
  "ad_id": "120230527342300676",
  "adset_id": null,
  "campaign_id": null,
  "date": "2025-07-22",
  "metrics": {...}
}
```

2. **AdSet 级别** (`level="adset"`)：
```json
{
  "ad_id": "120230527342250676",      // 向后兼容
  "adset_id": "120230527342250676",   // 广告组 ID
  "campaign_id": null,
  "date": "2025-07-22",
  "metrics": {...}  // 该 adset 下所有 ad 的指标总和
}
```

3. **Campaign 级别** (`level="campaign"`)：
```json
{
  "ad_id": "120230527342240676",      // 向后兼容
  "adset_id": null,
  "campaign_id": "120230527342240676", // 广告系列 ID
  "date": "2025-07-22",
  "metrics": {...}  // 该 campaign 下所有 ad 的指标总和
}
```

**注意事项**：
- ⚠️ **Account ID 格式**：数据库中存储的 `account_id` **不带 `act_` 前缀**
- 接口会自动处理前缀转换，用户输入 `1244295750378353` 或 `act_1244295750378353` 都可以
- ⚠️ **聚合级别**：adset 和 campaign 级别使用 MongoDB 聚合管道，按对应 ID 和日期分组汇总指标
- 如果查询无数据，请先使用 `POST /insights/sync/runs` 同步数据

### 2. 混合查询（数据库 + 实时 API）

**端点**：`POST /insights/query`
**数据源**：**MongoDB（历史数据）+ Facebook API（最近 3 天）**

**查询逻辑**：
```
1. 如果满足条件（level="ad", time_increment=1, 无 breakdowns）：
   ├─ 历史数据（今天 - 3 天之前）：从数据库查询
   └─ 实时数据（最近 3 天）：从 Facebook API 获取
2. 合并两部分数据，去重（以 API 数据为准）
3. 返回结果
```

**使用场景**：
- 需要查看最新数据（包括今天和昨天）
- 数据可能较慢（需要调用 Facebook API）

**请求示例**：
```bash
curl -X POST "http://localhost:8000/insights/query" \
  -H "Content-Type: application/json" \
  -H "X-User-Id: user123" \
  -d '{
    "ad_account_id": "act_1244295750378353",
    "since": "2025-10-01",
    "until": "2025-10-20",
    "level": "ad",
    "time_increment": 1
  }'
```

### 3. 异步拉取（大量数据）

**端点**：`POST /insights/jobs` + `GET /insights/jobs/{job_id}/result`

**使用场景**：
- 跨度很大的日期范围（例如 6 个月）
- 避免同步请求超时

**流程**：
```
1. POST /insights/jobs - 创建异步任务
   返回 job_id

2. GET /insights/jobs/{job_id} - 轮询任务状态
   返回 percent_complete 和 status

3. 等待 status = "Job Completed"

4. GET /insights/jobs/{job_id}/result - 获取结果
   返回完整的 insights 数据
```

## 常见问题

### Q1: 为什么查询 `/insights` 返回空数据？

**可能原因**：
1. **数据未同步**：数据库中没有该账号或日期范围的数据
2. **日期范围错误**：使用的日期范围与数据库中的实际数据不匹配
3. **Account ID 格式问题**：已修复，接口会自动处理前缀

**解决方法**：
```bash
# 1. 查看账号同步状态
curl -X GET "http://localhost:8000/insights/sync/runs" \
  -H "X-User-Id: user123"

# 2. 手动触发同步
curl -X POST "http://localhost:8000/insights/sync/runs" \
  -H "Content-Type: application/json" \
  -H "X-User-Id: user123" \
  -d '{
    "account_ids": ["1244295750378353"],
    "since": "2025-07-01",
    "until": "2025-10-31"
  }'
```

### Q2: 为什么 `/insights/query` 返回 500 错误？

**可能原因**：
- Facebook API 限流或超时
- 日期范围过大（建议使用 `/insights/jobs`）
- 网络问题

**解决方法**：
- 使用 `/insights` 查询数据库数据（推荐）
- 缩小日期范围
- 使用异步接口 `/insights/jobs`

### Q3: 同步后数据为什么不是最新的？

**原因**：
- 自动调度默认只同步到"今天 - 3 天"
- Facebook 数据有 24-48 小时延迟

**解决方法**：
- 使用 `POST /insights/query` 获取最近 3 天实时数据
- 手动触发同步，设置 `until` 为今天

### Q4: 如何重新同步历史数据？

**方法**：
手动触发同步，指定完整的日期范围即可。系统会自动 upsert，不会产生重复数据。

```bash
curl -X POST "http://localhost:8000/insights/sync/runs" \
  -H "Content-Type: application/json" \
  -H "X-User-Id: user123" \
  -d '{
    "account_ids": ["1244295750378353"],
    "since": "2024-01-01",
    "until": "2024-12-31"
  }'
```

### Q5: 如何选择合适的聚合级别（level）？

**三种级别的区别**：

1. **Ad 级别** (`level="ad"`)：
   - 返回每个广告的每日数据，无聚合
   - 数据粒度最细，记录数最多
   - 适用场景：查看单个广告的详细表现

2. **AdSet 级别** (`level="adset"`)：
   - 按广告组（AdSet）聚合，将同一广告组下所有广告的指标求和
   - 返回每个 AdSet 的每日汇总数据
   - 适用场景：对比不同广告组的效果，优化广告组预算分配

3. **Campaign 级别** (`level="campaign"`)：
   - 按广告系列（Campaign）聚合，将同一广告系列下所有广告的指标求和
   - 返回每个 Campaign 的每日汇总数据
   - 适用场景：查看整体广告系列表现，做高层级决策

**示例对比**（同一账号，同一日期范围）：
- Ad 级别：返回 25 条记录（25 个广告的数据）
- AdSet 级别：返回 7 条记录（7 个广告组的聚合数据）
- Campaign 级别：返回 7 条记录（7 个广告系列的聚合数据）

**注意**：各级别的总花费（Total Spend）应该相同，只是聚合粒度不同。

### Q6: 索引什么时候会被删除和重建？

**条件**：当同步的总天数 > 365 天时

**原因**：大批量写入时，索引会显著降低写入速度

**过程**：
1. 同步前删除所有非 `_id_` 索引
2. 执行批量写入
3. 同步后重建所有索引

**影响**：在重建索引期间，查询性能可能降低

## 最佳实践

### 1. 数据同步策略

- **日常查询**：使用 `/insights` 查询数据库
- **实时监控**：使用 `POST /insights/query` 获取最新数据
- **历史回溯**：使用 `POST /insights/sync/runs` 手动同步 + `/insights` 查询
- **大量数据**：使用 `/insights/jobs` 异步拉取

### 2. 性能优化

- **定期同步**：保持每日自动调度运行，避免积压
- **分批同步**：大范围日期分多次同步（每次不超过 30 天）
- **监控状态**：定期检查 `GET /insights/sync/runs` 确保同步正常

### 3. 错误处理

- **重试机制**：同步失败后可以直接重新触发，幂等设计
- **监控日志**：查看 API 日志了解详细错误信息
- **账号隔离**：单个账号失败不影响其他账号
